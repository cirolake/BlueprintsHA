How it works

Knob is clicked or turned→ Zigbee2MQTT publishes {"action": "..."}→ Trigger matches the action→ Condition checks it came from your knob→ Action changes the light

Blueprint header

name

The title shown in Settings → Automations & scenes → Blueprints.

description

The help text shown when you create an automation from the blueprint. The > joins lines into one paragraph, so a blank line is needed between bullet points to keep them as a list.

domain: automation

Makes this an automation blueprint, not a script blueprint.

homeassistant: min_version: "2024.10.0"

Home Assistant refuses to import the blueprint on older versions. 2024.10 is the first release that understands the newer triggers: / trigger: mqtt / action: syntax used below.

Inputs (what you fill in)

knob — Knob

Entity picker · MQTT entities only · one knob

Pick any one entity of the knob, such as its battery sensor or operation mode. The blueprint doesn't use that entity's state. It only uses it to find the knob's device, and from the device, the knob's name in Zigbee2MQTT. For several knobs, create one automation per knob.

light — CCT light

Entity picker · MQTT lights only · one light

The light the knob controls. Like the knob, it's only used to find the device's name in Zigbee2MQTT, because commands are sent to the light through MQTT.

advanced

collapsed: true

A folded section in the form, so the defaults stay out of the way.

sensitivity — Sensitivity

Default 1 · range 0.1–3

Each time you turn the knob, it reports a step size on a 0–255 scale, and a bigger turn gives a bigger number: the smallest click reports about 13 (5 %), a big turn about 133 (52 %). The blueprint multiplies it by this setting before sending it to the light. At 1 the light follows the knob exactly; at 0.5 every change is half as big.

base_topic — Zigbee2MQTT base topic

Default zigbee2mqtt

The first part of every Zigbee2MQTT MQTT topic. Only change it if you changed base_topic in the Zigbee2MQTT configuration.

Run mode

mode: single

What happens if the knob sends a new action while the previous one is still being handled.

ModeNew trigger during a runEffect with the knob
single (current)IgnoredA fast turn may skip some steps
queuedWaits its turnEvery step is applied, in order
restartStops the current run, starts the new oneSteps can be cut off halfway
parallelRuns at the same timeSteps can overlap and read stale values

max: 10

How many runs may wait (queued) or run at once (parallel).

With mode: single this line has no effect. It only matters if you switch back to queued or parallel.

max_exceeded: silent

When a trigger is dropped (in single mode: any trigger that arrives during a run), don't write a warning to the log. Without it, turning the knob would fill the log with "Already running" warnings.

Triggers

trigger_variables: base_topic

Makes the base_topic input available inside the trigger. Triggers are set up before the automation runs, so they can only use these special variables, not the normal variables block.

The five MQTT triggers

- trigger: mqtt
  topic: "{{ base_topic ~ '/+' }}"
  value_template: "{{ value_json.action | default('') }}"
  payload: brightness_step_up

topic — listens to zigbee2mqtt/<any device name>. The + matches exactly one level, so it receives every device's state message but not sub-topics such as /availability or /set.

value_template — reads the action field from the message. Messages without an action, such as a sensor reporting its temperature, give an empty value.

payload — the trigger only fires when that value equals this text exactly. That's why there are five triggers, one per action the knob sends in command mode:

ActionKnob gesture
toggleClick
brightness_step_upTurn right
brightness_step_downTurn left
color_temperature_step_upPress and turn right
color_temperature_step_downPress and turn left

Because the action is checked inside the trigger, ordinary state updates from your other Zigbee devices never start the automation.

Variables

knob, light, sensitivity

Copies of the inputs, so templates can use them. !input can't be used inside a template directly.

action

action: "{{ trigger.payload_json.action }}"

The action that fired this run, such as brightness_step_up. The actions below use it to choose what to do.

step

step: "{{ (trigger.payload_json.action_step_size | int(0) * sensitivity | float) | round(0) | int }}"

The knob's step size multiplied by sensitivity. The knob reports it on Zigbee's 0–255 scale: about 13 for the smallest click and about 133 for a big turn. The light uses the same scale, so no conversion is needed.

transition

transition: "{{ trigger.payload_json.action_transition_time | float(0) }}"

How long the knob asks the light to take to reach the new value, e.g. 0.1 s for one click or 0.3 s for a big turn. It's passed to the light, so changes fade smoothly instead of jumping. It doesn't change how big a step is; only sensitivity does that.

knob_topic and light_topic

knob_topic:  "{{ base_topic ~ '/' ~ device_attr(device_id(knob), 'name') }}"
light_topic: "{{ base_topic ~ '/' ~ device_attr(device_id(light), 'name') ~ '/set' }}"

The MQTT topics of the two devices. From the selected entity each one finds the device (device_id), reads the device's name (device_attr), and adds the base topic in front, e.g. zigbee2mqtt/Botão Giro Sala.

The knob publishes on its topic; the light listens for commands on its topic plus /set.

This works because the device name Home Assistant gets from Zigbee2MQTT is the friendly name. Renaming the device in Home Assistant is fine (that's stored separately). Renaming it in Zigbee2MQTT updates Home Assistant automatically.

Conditions

trigger.topic == knob_topic

The triggers accept actions from any device. This line keeps only messages from the knob you selected, so another remote that also sends toggle won't switch this light.

Actions

choose and mqtt.publish

Runs the first branch whose condition matches the action variable. Each branch sends one command straight to the light through Zigbee2MQTT (mqtt.publish to light_topic). Zigbee2MQTT and the light handle the rest: stepping from the current value, and stopping at the light's limits.

Click → {"state": "TOGGLE"}

The light switches to the opposite of its current state.

Turn right / left → brightness_step

{"brightness_step": 13, "transition": 0.1}     # one click right
{"brightness_step": -13, "transition": 0.1}    # one click left

Raises or lowers brightness by step on the light's 0–254 scale. This is the same command the knob would send if it were bound directly to the light. The module stops at its minimum brightness instead of turning off, and turning while the light is off does nothing.

Press and turn → color_temp_step

{"color_temp_step": -13, "transition": 0.1}    # press + right: cooler
{"color_temp_step": 13, "transition": 0.1}     # press + left:  warmer

Changes the color temperature by step mireds, Zigbee's unit for color temperature. Mireds run the opposite way to kelvin: more mireds means warmer. That's why turning right (cooler) sends a negative number. The FUT035Z+ supports 153–500 mireds, about 6500–2000 K; the light keeps itself inside that range.
